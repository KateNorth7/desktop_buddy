# Built-in AI and personal provider connections

The installed app selects **Built-in AI** by default. Everyone uses the same registration-free flow: install, complete onboarding and use the app. There are no invitations, access codes or user tiers. **Settings → AI → Services → AI connection** switches to **Use my API keys** without changing or removing saved credentials.

## Routing

All generation, coaching, goal actions, memory-assisted dialogue, screen understanding, background observations, import, web research and provider checks use the selected connection. Built-in generation uses the Claude Messages API with `claude-haiku-5-5` for primary work, responses, semantic verification and image descriptions. The server allowlist is explicit; personal connections retain their existing model/endpoint controls.

Built-in requests go from the Rust backend to `buddy-ai` in project `qrspcvglmmrputcltgxr`, then to fixed Claude HTTPS endpoints. No route returns an upstream key. The public `server/supabase/public.json` contains only the project URL and public `anon` client key; it is not a provider key or a Supabase service-role key.

An anonymous Supabase Auth session starts without user input. The app keeps its access/refresh session in a private local file, refreshes it automatically and checks the connection generation before sending/accepting responses. Provider credentials continue to use the existing OS vault, and the immutable macOS helper is unchanged. Switching modes invalidates old health receipts and pending-response authority; the sidebar checks the newly selected connection. A failed built-in request does not spend a user's personal-provider balance through silent fallback.

## Server boundary

- Platform JWT verification remains enabled. The function independently verifies each user token with this project's Auth service.
- Only two operations exist: Claude messages (`/anthropic/v1/messages`, optionally with one bounded `web_search` tool of at most three searches) and a single-model health read (`/anthropic/v1/models/<allowed model>`). Arbitrary URLs, remote image URLs, streaming, other tools and unlisted models are rejected. The gateway adds the `x-api-key`, `anthropic-version` and `anthropic-beta` headers upstream.
- Provider and service-role credentials exist only in Edge Function environment variables. Success health responses expose model IDs or a configuration boolean; upstream error bodies and account usage details are removed.
- Quota tables have RLS enabled and no grants for `anon` or `authenticated`. Only `service_role` can reserve usage. An advisory transaction lock makes global/user/minute reservations atomic across isolates.
- Counters store anonymous IDs, route counters, conservative reservation units and timestamps only. Prompts, screenshots, goals, search terms and model responses are not persisted by this gateway. Counter rows older than two days are pruned during the next successful gateway reservation. Supabase also retains the technical anonymous Auth records needed for automatic sessions.
- Default policy: 3,000 AI / 300 search calls globally per UTC day; 1,000 AI / 100 searches per anonymous session; 30 total calls per session per minute. A global 30,000,000-unit daily reservation ceiling also bounds use. A daily dollar ceiling of **$1.00 for all users together** (`budget_microusd_daily`, in micro-dollars) is enforced on top: each request reserves an estimate from Claude list prices (input bytes, a bounded output allowance and $0.01 per web search) and is settled to the provider's reported token and search usage after the response; once the day's spend reaches the ceiling, built-in requests return 429 until midnight UTC. At Haiku 5.5 prices the daily call limits (3,000 AI and 300 search calls) are reached before the dollar ceiling; the ceiling mainly bounds web searches at $0.01 each. Set a workspace spend limit in the Anthropic Console as the hard backstop; the gateway only sees traffic that passes through it. Text bytes, output-token budget weighted by eight, and image allowances contribute to units; **units are not a currency price**. Failed/timed-out reservations are not refunded. The gateway never retries a provider call. The existing client can try one fallback model for an interactive proposal; that additional request is counted separately and never replays an executed action. These are uniform anti-abuse limits, not feature tiers.
- **Per-user accounting.** After every settled response the gateway calls `buddy_record_ai_usage`, which adds one row per user, UTC day, route and model to `buddy_ai_usage_daily`: calls, input, output, cache-write and cache-read tokens, web searches and settled cost in micro-dollars. Numbers only, never content; rows older than 90 days are pruned. Developers read `buddy_ai_spend_by_user_day` (service role only), for example `select * from public.buddy_ai_spend_by_user_day where day = current_date order by usd desc;`.
- **Per-user daily cap.** `user_microusd_daily` (default $0.40) bounds each user's reserved spend per UTC day, on top of the shared `budget_microusd_daily`.
- **Spike detection and block.** After recording, a user is blocked until the end of the UTC day (`buddy_ai_blocks`, reason `spend_spike` or `call_burst`) when today's spend exceeds `spike_multiplier` (default 3) times their 7-day daily average and `spike_min_microusd` (default $0.20), or when their calls in the last 10 minutes exceed `burst_calls_10min` (default 60). A blocked user's reservations fail with 429; the response already delivered is not withdrawn. Lift a block by hand with `select public.buddy_unblock_ai('<user id>');`.
- **Developer alerts.** A newly blocked user triggers one Telegram message to the developers' chat with the user ID, the reason and the counters, and the unblock command; nothing else is sent. Configure the Edge Secrets `TELEGRAM_BOT_TOKEN` and `TELEGRAM_ALERT_CHAT_ID`; without them the block still applies and only a `gateway_user_blocked` log event is written.
- **Hard backstop.** The Anthropic Console has monthly, not daily, spend limits per organisation or workspace. Set one there as well; the daily limits above only see traffic that passes through this gateway.
- `buddy_ai_policy.enabled` is an immediate server kill switch. Limits can be changed by the owner without shipping a new app. The endpoint/public client key can be extracted from an installer, so authentication alone cannot stop determined misuse. Atomic global limits bound exposure; upstream provider spending caps should also be configured by the owner.

## Deployment and verification

1. Verify the exact project and organization before deployment. Use the owner's CLI profile; preserve other developers' sessions. Keep access tokens outside Git and command output.
2. Save a dedicated `ANTHROPIC_API_KEY` in Edge Secrets, and `TELEGRAM_BOT_TOKEN` with `TELEGRAM_ALERT_CHAT_ID` for spike alerts. Apply `server/supabase/ai-gateway.sql` **before** deploying a function version that calls `buddy_record_ai_usage` (it is idempotent and adds the daily dollar budget, per-user accounting, the per-user cap and spike blocks to an existing deployment); its initial policy is disabled. Until the SQL is applied, the newer function only logs `gateway_usage_failure` and keeps serving.
3. Enable anonymous sign-ins in this project's Auth settings. The app does not collect a name/email or show a login form for this technical session. Keep Auth's built-in abuse rate limits.
4. Deploy only the reviewed function: `supabase functions deploy buddy-ai --use-api --project-ref qrspcvglmmrputcltgxr --workdir server`. Do not use `--prune` or disable JWT verification to clear an unexplained failure.
5. Run `npm run test:gateway`. Verify quota rejection and denied public table/RPC access. Enable the policy only after these checks, then test actual model generation, web search, connection switching and a returning session. No private activity is needed for these checks.
6. Validate macOS and Windows, review the single additional Settings row, then publish one new synchronized version for both systems. Never replace the delivered 0.48.1 assets with different code.

Deployment does not enable profile collection or upload existing Feedback/history. Those remain separate product work.

## Focused live checks

The signed app's opt-in `--check-hero` rehearsal uses disposable synthetic data and real providers. `--only-hero-resume` checks Resume/focus/checkpoint only; `--only-hero-tail` checks Resume, a grounded summary and database-reopen recall with deterministic fixture setup. Use `BUDDY_AI_CONNECTION_MODE=built_in` or `personal` only for these `--check-*` commands. These checks never run on ordinary app startup or in automated mock-provider suites. `BUDDY_DIALOGUE_TRACE=true` is restricted to the supported synthetic CLI checks; it can print their request/response JSON, never provider headers, credentials or provider reasoning content.

## Daily operational availability

The [availability workflow](AI_SERVICE_AVAILABILITY.md) exercises anonymous sign-in and the existing two health routes daily, with sanitized output and no generation/search. Provider secrets stay in Supabase. Daily activity is not a guaranteed replacement for a paid plan's no-inactivity-pause policy.
